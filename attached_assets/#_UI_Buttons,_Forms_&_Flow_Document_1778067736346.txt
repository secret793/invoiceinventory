## 1. Devices / Trackers

### Layout
The Devices screen is the main tracker registry. At the top it shows two sets of stat widgets:
- **Device Statistics Widget** — Stat cards showing counts: Online, Offline, Damaged, Fixed, Lost, Unconfigured.
- **Device Status Filter Widget** — Clickable coloured buttons (Online / Offline / Damaged / Fixed / Lost / Received) with a live count on each. Clicking a button applies a status filter to the table below.

Below the widgets is the main table with a toolbar (search bar, column toggle, filter icon, and the header action buttons).

---

### Table Columns (18 total)

| Column | Notes |
|---|---|
| Device ID | Searchable |
| Device Type | JT701 / JT709A / JT709C |
| Batch Number | Hidden by default (toggleable) |
| Status | Colour badge |
| Date Received | Sortable |
| Distribution Point | Via `distributionPoint.name` relationship |
| SIM Number | Toggleable |
| SIM Operator | Hidden by default (toggleable) |
| Added By | Via `user.name` |
| Allocation Point | Toggleable, via `allocationPoint.name` |
| Created At | Hidden by default |
| Cancellation Reason | Hidden by default; shows the `cancelled_at` date as description |
| **Device Status** (iCloud) | Live badge — Online / Offline / Unknown |
| **Lock Status** (iCloud) | Live badge — Locked / Unlocked |
| **Battery Level** (iCloud) | Live percentage |
| **Location** (iCloud) | Latitude / Longitude |
| **Run Status** (iCloud) | Live badge |
| **GPS Time** (iCloud) | Last GPS ping time |

> The six iCloud columns are all toggleable. They are hidden by default and query the iCloud LBS API when shown. The base table query excludes UNCONFIGURED devices and orders by `date_received DESC`.

### Row Actions

#### Edit
Standard Filament edit action — opens the same form as "New Device" pre-filled with the record's current values.

#### Delete
Standard delete with confirmation dialog. Runs inside a DB transaction and fires the `DeviceObserver`.

#### Sync iCloud GUID / Re-sync GUID
- **Label:** "Sync iCloud GUID" if the device has no GUID yet; "Re-sync GUID" if it already has one.  
- **No form.** On click, calls `ICloudApiService::forAuthUser()->resolveDeviceGuid($record->device_id)` and saves the returned GUID to `devices.icloud_device_guid`.

---

### Bulk Actions

#### Sync iCloud GUIDs (Bulk)
No confirmation form. Builds a map of iCloud assets, matches each selected device's `device_id` to a `FAssetID`, and saves the GUID. Devices that already have a GUID are skipped.

#### Change Status (Bulk)

**Form:**

| Field | Type | Options |
|---|---|---|
| New Status | Select | UNCONFIGURED / CONFIGURED / ONLINE / OFFLINE / DAMAGED / FIXED / LOST |

**On Submit:** Updates `status` on all selected device records.

#### Transfer to Distribution Point (Bulk)

**Form:**

| Field | Type | Rules |
|---|---|---|
| Distribution Point | Select | Required — all DPs from `distribution_points` table |

**Validation before submit:**
- Rejects devices with status OFFLINE, LOST, or DAMAGED.
- Rejects devices already transferred (already have a `distribution_point_id`).
- Rejects devices already assigned to an agent.

**On Submit:** Creates a `Transfer` record for each device with `transfer_type = DISTRIBUTION` and `transfer_status = PENDING`.

#### Delete (Bulk)
Requires confirmation. Runs in a DB transaction and fires `DeviceObserver` for each record.

### Bulk Actions

#### Cancel Transfers

**Form:**

| Field | Type | Rules |
|---|---|---|
| Cancellation Reason | Textarea | Required, max 1000 characters |

**Validation:** All selected transfers must have `transfer_status = PENDING`.

**On Submit:**
- For DISTRIBUTION transfers: restores device's `distribution_point_id` to `from_location` and restores original `allocation_point_id`.
- For ALLOCATION transfers: restores device's `allocation_point_id` to `from_location`.
- Sets `transfer_status = CANCELLED` + `cancelled_at = now()`.
- **Deletes** the transfer record after cancelling.

---

#### Approve Transfers
**Form:** Confirmation dialog only (no fields).

**On Submit:**
- Sets device `status = RECEIVED`.
- Updates device `distribution_point_id` (or `allocation_point_id`) to the `to_location`.
- Sets `transfer_status = COMPLETED`.
- **Deletes** the transfer record after completing.

---

#### Delete (Bulk)
**Form:** Confirmation only.

**On Submit:** For PENDING transfers, reverts the device's location fields before deleting.

## 5. Distribution Points — View Page

### How to Access
Navigate to **Distribution Points** in the sidebar → click the **View** (eye) icon on any distribution point row.

### Layout
The view page shows:
1. **Other Items table** — two rows (35CM LOCKING CABLES, 3 METRES LOCKING CABLES) × columns (OK / DAMAGED / LOST / TOTAL)
2. **Device Status stats** — counts of ONLINE / OFFLINE / DAMAGED / FIXED / LOST / RECEIVED at this distribution point
3. **Status filter tabs** — clickable tabs to filter the device table by status
4. **Device table** with columns: Device ID, Device Type, Batch Number, Receipt Date, Status, SIM Number, SIM Operator, Added By, Added On
5. **Action buttons** — visible based on the status of selected devices

---

### Action Buttons

The button visibility is controlled by `determineButtonVisibility()`:
- **Collect Buttons** are shown when one or more selected devices have status RECEIVED.
- **Assign Buttons** are shown when no selected devices have status RECEIVED.

---

#### 5.1 Accept Devices
- **Shown when:** Some selected devices have `status = RECEIVED`.
- **Method:** `collectDevices()`
- **No form.** Confirmation only.

**On Submit:**
- Sets each selected device's `distribution_point_id` = this distribution point's ID.
- Changes status from RECEIVED to the device's previous non-RECEIVED status (device is now "at" this DP).
- Clears `allocation_point_id = null`.

---

#### 5.2 Send to Allocation Point
- **Shown when:** No selected devices have RECEIVED status.
- **Method:** `sendToAllocationPoint()` → dispatches `open-allocation-modal` event.

**Modal form:**

| Field | Type | Rules |
|---|---|---|
| Allocation Point | Select | All allocation points. Required. |

**On Confirm** (`confirmSendToAllocationPoint()`):
- Validates none of the selected devices have status RECEIVED.
- Creates a `Transfer` record: `transfer_type = ALLOCATION`, `transfer_status = COMPLETED`, `received = true`.
- Updates device: `allocation_point_id = selectedAP`, `status = RECEIVED`.
- Clears `distribution_point_id = null`.

---

#### 5.3 Return Device to Inventory
- **Method:** `returnDeviceToInventory()`
- **No form.** Confirmation only.

**Validation:** None of the selected devices may have status RECEIVED.

**On Submit:**
- Creates a `Transfer` record: `transfer_type = DISTRIBUTION`, `transfer_status = COMPLETED`.
- Sets device `distribution_point_id = null`, `allocation_point_id = null`.
- Device effectively goes back to unassigned inventory.

---

#### 5.4 Accept Returned Device
- **Method:** `acceptReturnedDevice()`
- **No form.** Confirmation only.

**On Submit:**
- Finds devices at this DP with status PENDING (i.e. returned from field).
- Looks up the latest transfer for each device.
- Restores device status to `transfer.original_status` (default: `'ONLINE'` if null).
- Sets `distribution_point_id = this->record->id`.
- **Deletes** the `device_retrievals` record for each device.

---

#### 5.5 Reject Device(s)
- **Method:** `rejectReturnedDevice()`
- **No form.** Confirmation only.

**On Submit:**
- Finds devices with PENDING status at this DP.
- Looks up the `device_retrieval` record with `retrieval_status = RETURNED`.
- Sets device `status = RETRIEVED`.
- Clears `distribution_point_id = null`.
- Updates `device_retrieval`: `retrieval_status = RETRIEVED`, `transfer_status = pending`.

---

#### 5.6 Change Device Status
- **Method:** `changeDeviceStatus()` → dispatches `open-status-modal` event.

**Modal form:**

| Field | Type | Options |
|---|---|---|
| Status | Select | ONLINE / OFFLINE / DAMAGED / FIXED / LOST |

**Validation:** None of the selected devices may have status RECEIVED.

**On Submit:** Updates `devices.status` for all selected devices.

---

#### 5.7 Send to Another Distribution Point
- **Method:** `sendToAnotherDistributionPoint()`

**Modal form:**

| Field | Type | Rules |
|---|---|---|
| Target Distribution Point | Select | All distribution points. Required. |

**Validation:**
- None of the selected devices may have status RECEIVED.
- No pending transfers may exist for the selected devices.

**On Submit:**
- Creates a `Transfer` record: `transfer_type = DISTRIBUTION`, `transfer_status = COMPLETED`, `received = true`.
- Sets device `distribution_point_id = selectedTargetDP`.
- Sets device `status = RECEIVED`.

**On Submit — Step by step:**

1. **DB Transaction begins.**
2. Validates at least one device is selected; throws if none.
3. Validates the selected Receipt exists and `canBeUsed()` (has `used > 0`); throws if not.
4. Derives `transaction_type` and `transaction_reference` directly from the receipt object (not from the form fields, because disabled inputs are unreliable across Livewire).
5. Checks that none of the selected devices already have an `AssignToAgent` record — throws "already dispatched" if any do.
6. Checks that none of the selected devices have `status = RECEIVED` — throws if any do.
7. For each selected device:
   - Creates an `AssignToAgent` record with all form data.
   - Creates a `ConfirmedAffixed` record with `status = PENDING`.
   - Creates a `DispatchLog` record.
   - Clears `device.allocation_point_id = null`.
8. **DB::commit()**
9. **Outside the transaction** — calls iCloud `addRouteDeparture` for each device with the dispatch payload (FAssetID, FVehicleName, FDepartureType=0, FFinishType, FIsLbsAnalysis=1, FPlanStartTime, FPlanEndTime, optional: FDriverName, FWaybill, FGoods, FCargoDescribe, FContainerNo, FConsignee, FRouteName).
   - On iCloud success: saves `icloud_waybill_guid` on both the `AssignToAgent` and `ConfirmedAffixed` records.
   - On iCloud failure: **does NOT roll back the DB.** Shows a persistent warning notification with the device ID and the failure reason (e.g. "Result 110 — Device not registered in iCloud").
10. Clears `selectedDevices = []`.
11. Shows a success or warning notification.

## 12. Device Flow Summary

This section describes the complete lifecycle of a device — from the moment it enters the warehouse to the moment it is physically retrieved from the field.

---

```
WAREHOUSE INTAKE
      │
      ▼
[1. Devices / Trackers — Create]
   Device is registered with:
   - device_id, device_type, batch_number
   - date_received, SIM details (if configured)
   - Status: UNCONFIGURED → CONFIGURED after SIM is added
      │
      ▼
[2. Bulk Transfer to Distribution Point]
   (Devices screen → Bulk Action: Transfer to Distribution Point)
   - Transfer record created: type=DISTRIBUTION, status=PENDING
   - Device status remains unchanged
      │
      ▼
[3. Transfer Approved]
   (Transfers screen → Bulk Action: Approve Transfers)
   - Device status → RECEIVED
   - Device distribution_point_id set to the destination DP
   - Transfer record deleted after completing
      │
      ▼
[4. Distribution Point — Accept Devices]
   (Distribution Points → View → Accept Devices button)
   - Device status RECEIVED → ONLINE (or previous status)
   - Device is now "at" the distribution point
   - allocation_point_id cleared
      │
      ▼
[5. Distribution Point — Send to Allocation Point]
   (Distribution Points → View → Send to Allocation Point button)
   - Transfer record created: type=ALLOCATION, status=COMPLETED
   - Device status → RECEIVED
   - Device allocation_point_id set to the selected AP
   - distribution_point_id cleared
      │
      ▼
[6. Allocation Point — Accept Devices]
   (Allocation Points → View page — devices with RECEIVED status appear)
   - No explicit "accept" needed — devices appear automatically.
   - Officer may change status (ONLINE/OFFLINE/DAMAGED/etc.)
      │
      ▼
[7. Data Entry — Dispatch]
   (Data Entry → Assignment View → Dispatch button)
   - Officer selects device(s) from the allocation point device table
   - Fills in Receipt, Vehicle, Regime, Destination, Route, Driver, ETD, ETA, etc.
   - DB records created: AssignToAgent + ConfirmedAffixed (status=PENDING) + DispatchLog
   - iCloud trip (waybill) created via addRouteDeparture API
   - device.allocation_point_id cleared
      │
      ▼
[8. Confirmed Affixed — Pick for Affixing]
   (Confirmed Affixed screen → Pick for Affixing row action or bulk action)
   - Affixing officer physically attaches tracker to vehicle
   - Records the affixing_date (defaults to now)
   - Creates DeviceRetrieval record (status=NOT_RETRIEVED)
   - Creates ConfirmedAffixLog record (status=AFFIXED)
   - Deletes AssignToAgent and ConfirmedAffixed records
      │
      ▼
[9. Monitoring — Device in Field]
   (Monitoring screen — shows live overdue hours and overstay days)
   - Table polls every 10 seconds
   - Overdue hours counts from affixing_date
   - Overstay days calculated from affixing_date / route threshold
   - Officers may add notes via "Add Note" row action
      │
      ├─── [IF OVERSTAY] ────────────────────────────────────────────────────────┐
      │                                                                          │
      │   [9a. Device Retrievals — Generate Overstay Bill]                      │
      │        (Overdue Bills row action)                                        │
      │        - Invoice generated: overstay_days × route.base_usd_amount       │
      │          × exchange_rate_gmd_usd                                         │
      │        - payment_status → PP (Pending Payment)                          │
      │        - Device cannot be retrieved until payment confirmed               │
      │        │                                                                 │
      │        ▼                                                                 │
      │   [9b. Finance Approval OR Admin Waiver]                                │
      │        Finance Officer: Approve Payment → payment_status = PD (Paid)    │
      │        Super Admin: Admin Waiver → marks record as waived                │
      │                                                                          │
      └──────────────────────────────────────────────────────────────────────────┘
      │
      ▼
[10. Device Retrievals — Retrieve Device]
   (Device Retrievals → row action: Retrieve Device)
   - Physical device is removed from vehicle
   - If SAD transaction and last device on receipt: T1 Validation Reference required
   - If overdue and non-privileged user: Receipt Number required
   - device_retrievals.retrieval_status → RETRIEVED
   - devices.status → RETRIEVED
   - Observer syncs Monitoring table
      │
      ├─── [IF DEVICE RETURNED TO OUTSTATION] ──────────────────────────────────┐
      │   (Device Retrievals → Return to Outstation row action)                 │
      │   - Officer selects Distribution Point                                  │
      │   - devices.status → PENDING                                            │
      │   - devices.distribution_point_id → selected DP                         │
      │   - device_retrievals archived (not deleted) — invoices preserved        │
      │   - monitoring record deleted                                            │
      │   - Device is back at Distribution Point with PENDING status            │
      │   - Distribution Point officer uses "Accept Returned Device"            │
      │     or "Reject Device(s)" to process it (see Section 5.4 / 5.5)        │
      └──────────────────────────────────────────────────────────────────────────┘
      │
      ▼
[11. Device back in Inventory / Allocation Point]
   - Retrieval Officer may transfer device back to an AP or DP
   - Device can be re-dispatched by repeating from Step 7
   - Device may be marked DAMAGED, FIXED, LOST etc. at any point
     via "Change Device Status" actions at DP or AP level
```

---

### Key Status Definitions

| Status | Meaning |
|---|---|
| `UNCONFIGURED` | Device entered but SIM not yet installed |
| `CONFIGURED` | SIM installed; ready to deploy |
| `ONLINE` | Active and GPS-reporting in the field or at an AP/DP |
| `OFFLINE` | Not reporting GPS |
| `DAMAGED` | Physical damage reported |
| `FIXED` | Damage repaired |
| `LOST` | Device cannot be located |
| `RECEIVED` | In transit between locations (e.g. being transferred to DP or AP) |
| `PENDING` | Returned from field, awaiting acceptance/rejection at a DP |
| `RETRIEVED` | Physically retrieved from vehicle after field deployment |
